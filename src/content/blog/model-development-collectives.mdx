The [memory lesson](/blog/model-development-training-memory/) ended with a trade. Sharding optimiser state, gradients and parameters across $d$ GPUs shrinks each GPU's share, but nothing is free: a GPU that owns only an eighth of the gradients still needs the other seven eighths of the information to update correctly. That information has to cross a network.

This lesson counts the crossing. By the end you should be able to:

- say what an all-reduce, all-gather and reduce-scatter leave on each GPU, and why one all-reduce is the other two in sequence;
- derive the time of a ring collective from a latency term and a bandwidth term, and tell which one dominates for a given message size;
- compute the per-step communication of plain data parallelism, each ZeRO stage, tensor parallelism and pipeline parallelism;
- explain why only the communication that cannot overlap computation lengthens a step.

Prerequisites: the [training-memory lesson](/blog/model-development-training-memory/) for the ZeRO stages, and the [Transformer lesson](/blog/foundations-transformer/) for layers and hidden width. A **rank** is one process in the job; assume one rank per GPU. The [decision guide](/blog/model-development-choosing-parallelism/) that follows uses everything here to choose a layout.

## The four collective operations

A **collective** is an operation that every rank in a group calls together, as opposed to one rank sending to another. NVIDIA's NCCL (the NVIDIA Collective Communications Library) documentation defines the ones that matter for training. *Reported, [NCCL 2.32.3 user guide](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html):*

| Collective | Each rank starts with | Each rank ends with |
|---|---|---|
| All-reduce | its own $N$ values | the same $N$ values, reduced (for example summed) across ranks |
| All-gather | its own $N$ values | all $k$ ranks' values concatenated: $kN$ values, in rank order |
| Reduce-scatter | its own array | one equal-sized block of the reduced array, chosen by its rank |
| All-to-all | $k$ chunks | chunk $i$ from every rank $i$: each rank sends its $j$-th chunk to rank $j$ |

The same page states the identity this lesson leans on: "Executing ReduceScatter, followed by AllGather, is equivalent to the AllReduce operation." It also requires every rank to call a collective with the same count and data type, and warns that failing to do so can cause hangs, crashes or data corruption.

Map these onto training. Data parallelism gives each rank a different batch, so each rank computes different gradients; to apply the same update everywhere, the gradients must be **summed across ranks and delivered to all of them**: an all-reduce. When ZeRO gives each rank ownership of one shard of the optimiser state, a rank only needs the reduced gradients **for its own shard**: a reduce-scatter. And when parameters are sharded, a layer about to run needs **everyone's shards back in one piece**: an all-gather.

<details>
  <summary>Check: ZeRO stage 2 replaces the gradient all-reduce with a reduce-scatter. Why can the rank skip the rest of the all-reduce?</summary>
  <p>The all-reduce is a reduce-scatter followed by an all-gather. After the reduce-scatter each rank already holds the fully summed gradients for its own shard, which is all its optimiser needs. The all-gather would hand it gradients for shards it does not update. The parameters it updates do have to be shared afterwards, which is the all-gather that reappears in ZeRO's accounting below.</p>
</details>

## A ring all-reduce, step by step

There are many algorithms for an all-reduce. The **ring** is the one to understand first, because its bandwidth cost is optimal and its cost is easy to derive. Arrange the $p$ ranks in a circle and cut every rank's tensor into $p$ chunks. Each step, every rank sends one chunk to its right-hand neighbour and receives one from its left, so all links are busy at once.

- **Reduce-scatter phase**, $p - 1$ steps: each rank adds the chunk it receives to its own copy and forwards the running sum. After $p - 1$ steps every chunk's sum has visited all ranks, and each rank holds one fully reduced chunk.
- **All-gather phase**, another $p - 1$ steps: each rank forwards its finished chunk, and receivers copy it. After $p - 1$ more steps everyone has every sum.

Count what each rank sends. Each step it sends one chunk of $n/p$ bytes, where $n$ is the size of the whole tensor. The all-reduce has $2(p - 1)$ steps, so each rank sends

$$
2\,\frac{p-1}{p}\,n \ \text{bytes}.
$$

- $p$: ranks in the ring.
- $n$: size of the full tensor being reduced, in bytes.
- $\frac{p-1}{p}$: the share of the tensor a rank must receive from others; it already holds its own $\frac{1}{p}$.

Intuition: the amount each rank sends **barely depends on how many ranks there are**. It grows from $n$ at two ranks to just under $2n$ for a large ring. Four ranks send $1.5n$ each, as the figure's counter shows. This is why a ring is said to be bandwidth-optimal: nccl-tests' explanation of its bus-bandwidth formula derives the same $2(n-1)/n$ factor as a best case for any algorithm built from point-to-point sends ([nccl-tests PERFORMANCE.md](https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md)).

## The cost of a collective: latency plus bandwidth

To turn bytes into seconds, use the classic latency-bandwidth (α–β) model. *Reported, [Thakur, Rabenseifner and Gropp (2005), §3–4](https://web.cels.anl.gov/~thakur/papers/ijhpca-coll.pdf):* sending a message of $m$ bytes between two processes takes $\alpha + m\beta$, and their ring all-gather takes

$$
T_{\text{ring}} = (p-1)\,\alpha + \frac{p-1}{p}\,n\beta .
$$

- $\alpha$: the fixed **latency** of one message, in seconds, whatever its size.
- $\beta$: seconds per byte, the inverse of the effective bandwidth $B$; this lesson writes $n\beta$ as $n/B$.
- $(p - 1)$: the number of steps, each paying one latency.

The paper notes that the bandwidth term "cannot be reduced further because each process must receive" $n/p$ data from each of the $p - 1$ others. A reduce-scatter has the same communication terms, plus arithmetic for the additions that this lesson ignores. An all-reduce is both, so it costs twice:

$$
T_{\text{all-reduce}} \approx 2(p-1)\,\alpha + 2\,\frac{p-1}{p}\,\frac{n}{B}.
$$

**Worked example** (*Derived*, with assumed $\alpha = 5\ \mu\text{s}$ and $B = 40$ GB/s, where GB is $10^9$ bytes). An all-gather of $n = 1$ GB on 8 ranks: latency $7 \times 5\ \mu\text{s} = 35\ \mu\text{s}$; bandwidth $\frac{7}{8} \times \frac{1\ \text{GB}}{40\ \text{GB/s}} = 21.9$ ms. The latency is invisible. Now an all-reduce of 8.75 GB on 32 ranks: bandwidth term $2 \times \frac{31}{32} \times \frac{8.75}{40} = 0.424$ s, latency $62 \times 5\ \mu\text{s} = 0.31$ ms.

Small messages flip the picture. A **1 MiB** all-reduce on 32 ranks has the same 0.31 ms of latency, but its bandwidth term is only $2 \times \frac{31}{32} \times \frac{1{,}048{,}576}{40 \times 10^9} = 0.051$ ms. Latency is **six times** the transfer time.

### Where latency and bandwidth trade places

Setting the two terms of the ring all-gather equal finds the message size where they cost the same:

$$
(p-1)\,\alpha = \frac{p-1}{p}\,\frac{n^*}{B}
\quad\Longrightarrow\quad
n^* = p\,\alpha\,B .
$$

- $n^*$: the **crossover size**. Below it latency dominates; above it bandwidth does.

With 32 ranks, 5 µs and 40 GB/s, $n^* = 32 \times 5 \times 10^{-6} \times 40 \times 10^{9} = 6.4$ MB. The crossover **grows with the ring**: more ranks means more steps, each paying α. That is one reason real libraries switch to tree or hierarchical algorithms for small messages and large groups; the model above is the ring alone.

### Algorithm bandwidth versus bus bandwidth

When you measure a collective, two "bandwidths" can be reported, and confusing them can make a link look twice as fast or twice as slow. *Reported, [nccl-tests PERFORMANCE.md](https://github.com/NVIDIA/nccl-tests/blob/master/doc/PERFORMANCE.md):* **algorithm bandwidth** is the tensor size divided by the time, $S/t$. **Bus bandwidth** multiplies it by a collective-specific factor so that the number reflects how hard the links worked, independent of the rank count: $2(n-1)/n$ for all-reduce and $(n-1)/n$ for all-gather and reduce-scatter, where $n$ is the rank count.

Example (*Derived*): an all-reduce of 1 GB on 8 ranks that takes 50 ms has algorithm bandwidth 20 GB/s and bus bandwidth $20 \times 2 \times \frac{7}{8} = 35$ GB/s. The 35 is the one to compare with a link's rated speed, and the one that corresponds to $B$ in the formulas above. Always state which you are quoting.

## Why gradients travel in buckets

Data parallelism could wait for the whole backward pass and then all-reduce every gradient at once. That would serialise communication after computation. Instead, frameworks group gradients into **buckets** and reduce each bucket as soon as its gradients are ready, while backward continues on earlier layers. *Reported, [PyTorch 2.15 DistributedDataParallel](https://docs.pytorch.org/docs/2.15/generated/torch.nn.parallel.DistributedDataParallel.html):* `bucket_cap_mb` sets the bucket size, "a default size of 25 MiB will be used", and "gradient reduction of each bucket can potentially overlap with backward computation."

Buckets change only the latency term. Splitting gradients of $G$ bytes into $k = \lceil G / b \rceil$ buckets of at most $b$ bytes runs $k$ all-reduces:

$$
T_{\text{buckets}} \approx k \cdot 2(p-1)\,\alpha + 2\,\frac{p-1}{p}\,\frac{G}{B}.
$$

- $k$: number of buckets, each a separate collective paying its own latency.
- $G$: total gradient bytes; the bandwidth term is the same however you split them.

**Worked example** (*Derived*, same assumed link): a 7-billion-parameter model's BF16 gradients are $G = 14$ GB. On 8 ranks the bandwidth term is $2 \times \frac{7}{8} \times \frac{14}{40} = 0.6125$ s.

| Bucket size | Buckets $k$ | Latency term | Total |
|---|---:|---:|---:|
| 25 MiB (PyTorch default) | 535 | 37.5 ms | 0.650 s |
| 1 MiB | 13,352 | 935 ms | 1.547 s |
| 1 GiB | 14 | 1.0 ms | 0.614 s |

Tiny buckets drown in latency. Huge buckets win on this formula but defeat the purpose: the first one cannot start until a gigabyte of gradients exists, so less of the communication overlaps backward. The bucket size is a trade between latency and overlap that only a measurement settles.

## What each ZeRO stage moves per step

Now return to the memory saving. *Reported, [ZeRO v3 §7](https://arxiv.org/html/1910.02054v3#S7):* with $\Psi$ the number of parameters, standard data parallelism's all-reduce moves $2\Psi$ per step, as a reduce-scatter plus an all-gather of $\Psi$ each. Partitioning optimiser state and gradients replaces it with a reduce-scatter of gradients ($\Psi$) and an all-gather of the updated parameters ($\Psi$): "$\Psi + \Psi = 2\Psi$, exactly the same as the baseline DP." Partitioning parameters as well adds parameter all-gathers in forward and backward: "The total volume is therefore $3\Psi$ which is 1.5x compared to the baseline."

| Policy | Collectives per step | Volume (ZeRO §7) |
|---|---|---:|
| Replicated data parallel | all-reduce of gradients | $2\Psi$ |
| ZeRO stage 1 or 2 | reduce-scatter of gradients, all-gather of updated parameters | $2\Psi$ |
| ZeRO stage 3 | all-gather of parameters in forward, again in backward, reduce-scatter of gradients | $3\Psi$ |

ZeRO's $\Psi$ per collective is the ring's $\frac{p-1}{p}\Psi$ rounded up for large $p$. Putting the volumes through the ring model with the worked example's numbers (*Derived*: $\Psi = 7 \times 10^9$, BF16, 8 ranks, 25 MiB buckets, assumed 5 µs and 40 GB/s):

| Policy | Bytes sent per rank | Time per step |
|---|---:|---:|
| Replicated, stage 1, stage 2 | 24.5 GB | 0.650 s |
| Stage 3 | 36.75 GB | 0.975 s |

So the memory lesson's trade, in numbers: stage 3 cut persistent state from 26.25 GB (stage 2) to 14 GB per rank, and costs 12.25 GB more traffic per rank per step. Whether that matters depends on the next section.

<details>
  <summary>Check: stages 1 and 2 move the same volume as plain data parallelism. Do they therefore take the same time?</summary>
  <p>Not necessarily. The volume is the same, but the order differs. Plain data parallelism's gradient all-reduce can overlap backward bucket by bucket. In stages 1 and 2 the all-gather of updated parameters can only start after the optimiser step that produces them, so it cannot hide behind that step's backward pass. Whether an implementation overlaps it with the next forward pass is an implementation detail to check, not something the volume tells you.</p>
</details>

## Tensor and pipeline parallelism move activations

Data parallelism and ZeRO move **parameters and gradients**, once per optimiser step. The two model-parallel strategies move **activations**, and they do it inside the computation.

**Tensor parallelism** splits each layer's weight matrices across $t$ ranks. *Reported, [Megatron-LM (2021) §2.3 and §3.2](https://arxiv.org/html/2104.04473v5):* the Transformer's MLP and self-attention blocks are partitioned so that each needs "only two all-reduce operations in the forward pass" and two in the backward pass, per layer. Each all-reduce carries a $b \times s \times h$ activation tensor:

$$
\text{bytes per all-reduce} = b\,s\,h\,c, \qquad \text{all-reduces per microbatch} = 4L .
$$

- $b$: microbatch size in sequences; $s$: sequence length in tokens; $h$: hidden width.
- $c$: bytes per value, 2 for BF16; $L$: number of Transformer layers.

**Worked example** (*Derived*): $b = 1$, $s = 2048$, $h = 8192$, BF16, $L = 80$. Each all-reduce carries $2048 \times 8192 \times 2 = 32$ MiB, and one microbatch runs $4 \times 80 = 320$ of them. On a tensor-parallel group of $t = 8$, each rank sends $2 \times \frac{7}{8} \times 320 \times 32\ \text{MiB} \approx 18.8$ GB **per microbatch**. At an assumed 40 GB/s that is 0.47 s; at an assumed 300 GB/s, closer to what a fast in-node link offers, 63 ms.

Two things make this traffic different from data parallelism's. It recurs **every microbatch**, not once per optimiser step. And it sits on the **critical path**: the next operation needs the all-reduced activation, so by default there is nothing to hide it behind. This is the arithmetic behind Megatron's first takeaway, that tensor parallelism belongs inside the fast links of one server; the [review](/paper-reviews/megatron-ptd-p/#reported-what-the-paper-measured) quotes it with its conditions.

**Pipeline parallelism** gives each of $p$ ranks a contiguous block of layers. Between stages it sends one activation tensor forward and one gradient back per microbatch, point to point, which is far less traffic. Its cost is time, not bytes. *Reported, Megatron-LM §2.2.1:* in a schedule that flushes the pipeline every step, the fraction of ideal compute time spent idle in the **bubble** is

$$
\text{bubble} = \frac{p-1}{m},
$$

- $p$: pipeline stages; $m$: microbatches per optimiser step.

and the interleaved schedule of §2.2.2, which gives each rank $v$ smaller blocks of layers, divides it by $v$. **Worked example** (*Derived*): with $p = 8$, $m = 32$ microbatches give a bubble of $7/32$, about 22% of ideal time, so the stages are busy $32/39 = 82\%$ of the step. With only $m = 4$ the bubble is 175% of ideal time and the stages are busy 36% of it. Interleaving with $v = 2$ halves the 22% to 11%. The [decision guide](/blog/model-development-choosing-parallelism/#pipelines-and-the-bubble) shows the schedule as a chart.

## Overlap decides what you pay

A step is not the sum of its compute and its communication. Some collectives can run while unrelated computation continues; others must finish before the next operation can start. For communication that could fully overlap a stretch of compute of length $C$, the step time lies between two bounds:

$$
\max(C, T_{\text{comm}}) \;\le\; T_{\text{step}} \;\le\; C + T_{\text{comm}} .
$$

- $C$: compute time available to overlap with, for example the backward pass.
- $T_{\text{comm}}$: the communication time from the model above.

Only the part outside the compute, the **exposed communication**, lengthens the step. The best case exposes $\max(0, T_{\text{comm}} - C)$; the worst exposes all of it. With 1 s of backward, the 0.65 s of the 7B example could disappear entirely, while stage 3's 0.97 s might still just about hide; at 0.5 s of backward, neither can.

This is a bound, not a prediction (*Derived*). Communication and compute compete for the same memory bandwidth and GPU cores even when they overlap, and dependencies decide what can overlap at all. Finding the longest chain of dependent compute and communication, the critical path, requires a profile of the real step.

  <p>No. Time inside collectives that overlaps compute does not lengthen the step. What matters is how much of the step would disappear if communication were free, which is the exposed part on the critical path. Measure it by comparing against a run with the collective removed or with communication-free compute, holding everything else fixed.</p>
</details>

## Evidence and its limits

- **Reported:** the collective definitions and the ReduceScatter-plus-AllGather identity (NCCL 2.32.3 guide); the ring all-gather cost $(p-1)\alpha + \frac{p-1}{p}n\beta$ (Thakur et al. 2005); the bus-bandwidth factors (nccl-tests); DDP's 25 MiB default bucket and possible overlap (PyTorch 2.15); ZeRO's $2\Psi$ and $3\Psi$ volumes (ZeRO v3 §7); four tensor-parallel all-reduces per layer and the $(p-1)/m$ bubble (Megatron-LM v5).
- **Derived:** every time in this lesson, under assumed values of α and B that are illustrations, not measurements of any particular hardware; the crossover $n^* = p\alpha B$; the bucket trade-off; the overlap bounds.
- **Hypothesis:** that communication is the bottleneck of any particular job. It becomes a finding only with a profile showing exposed communication on the critical path.
- **Unknown:** how a given cluster's topology, collective algorithm choices and contention change these numbers. The α–β ring is the simplest model that explains why size, rank count and overlap matter; real libraries use trees, hierarchies and size thresholds.
