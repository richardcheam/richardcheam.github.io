The two earlier lessons give you the parts: a [memory ledger](/blog/model-development-training-memory/) that says what each GPU must store, and a [communication model](/blog/model-development-collectives/) that says what it must send. This guide puts them in order. It does not tell you the best layout for your cluster; nothing on paper can. It tells you which layout to try first, and what result from that pilot would make you change it.

Learning objectives:

- order the decisions so that each one is made with the information it needs;
- compute, for a candidate layout, its persistent state, its data-parallel traffic, its tensor-parallel traffic and its pipeline bubble;
- explain why a layout that looks cheaper on paper can lose in a measured comparison;
- design a short pilot that tests the assumption your choice depends on.

Throughout, $t$, $p$ and $d$ are the tensor-parallel, pipeline-parallel and data-parallel degrees. For a dense model on a regular grid of GPUs, the device count is $G = t \cdot p \cdot d$.

## The procedure

Work through the questions in this order. Each answer narrows the next.

| Step | Question | Tool | What would overturn the answer |
|---|---|---|---|
| Fix the batch | How many tokens per optimiser step, at what sequence length? | Training plan | A learning-rate or convergence result that needs a different batch |
| Fit the state | Does replicated data parallelism fit? If not, which ZeRO stage is the smallest that fits with headroom? | [Memory estimator](/blog/model-development-training-memory/#shard-ownership-then-do-the-arithmetic) | A measured peak above capacity |
| Fit the activations | Do one microbatch's activations fit beside the state? | Profile, or the activation analysis of [Korthikanti et al.](https://arxiv.org/abs/2205.05198) | Out-of-memory at the planned sequence length |
| Add model parallelism only if needed | Tensor parallelism inside a server; pipeline stages across servers | Megatron's takeaways, below | A measured comparison on your network |
| Check communication | How much traffic is exposed, best and worst case? | [Planner](#data-parallel-communication) | A profile showing exposed collectives on the critical path |
| Pilot | Which assumption is weakest? | [Bounded experiment](#a-bounded-experiment) | The experiment's result |

The order matters because the early answers are cheap to get and rule out whole families of layouts. There is no point tuning bucket sizes for a layout whose optimiser state does not fit.

## Fit the state, then the activations

Start with the cheapest layout: replicated data parallelism, where every GPU holds everything and only gradients travel. If the [memory ledger](/blog/model-development-training-memory/#start-with-an-explicit-ledger) says the state fits with room for activations, stop there.

If it does not fit, prefer ZeRO's stages in order. Stages 1 and 2 shrink the state **without adding traffic**: they move $2\Psi$ per step, the same as plain data parallelism (*Reported, [ZeRO v3 §7](https://arxiv.org/html/1910.02054v3#S7)*). Stage 3 shrinks it further at $3\Psi$, 1.5 times the traffic. So the rule of thumb (*Derived*) is: use the lowest stage that leaves enough headroom, and move to stage 3 only when you need the memory.

Sharding cannot help if a single microbatch's **activations** do not fit, or if the global batch is too small to give every data-parallel rank at least one sequence. Both are reasons to split the model itself.

## Add model parallelism only when you must

Model parallelism splits each forward pass across GPUs, so it costs communication inside the computation (see the [collectives lesson](/blog/model-development-collectives/#tensor-and-pipeline-parallelism-move-activations)). Megatron-LM's study on DGX A100 servers (8 GPUs per server, NVLink inside, eight 200 Gb/s InfiniBand adapters between) gives three takeaways. *Reported, [Narayanan et al. (2021)](https://arxiv.org/html/2104.04473v5), quoted:*

- Takeaway #1, §3.2: "tensor model parallelism should generally be used up to degree $g$ when using $g$-GPU servers", with pipeline parallelism used to scale across servers.
- Takeaway #2, §3.3.2: "a total model-parallel size of $M = t \cdot p$ should be used" so that the model fits in GPU memory, with data parallelism scaling to more GPUs.
- Takeaway #3, §3.4: "The optimal microbatch size $b$ depends on the throughput and memory footprint characteristics of the model."

These are conclusions from one family of servers and models. They transfer to the extent that your hardware has the same shape: a fast link inside a server and a slower one between servers. The [review](/paper-reviews/megatron-ptd-p/) examines the experiments behind them.

### Pipelines and the bubble

A pipeline's traffic is small, but it idles. With a flush schedule, the stages sit idle for $\frac{p-1}{m}$ of the ideal compute time, where $m$ is the number of microbatches per step (*Reported, Megatron-LM §2.2.1*). Reshape the schedule to see why $m$ must be large compared with $p$:

The bubble couples the pipeline to the batch. For sequences of uniform length $S$, the tokens per optimiser step are

$$
B_{\text{tok}} = d \cdot m \cdot b \cdot S .
$$

- $d$: data-parallel replicas; $m$: microbatches per replica per step.
- $b$: sequences per microbatch; $S$: tokens per sequence.

Fix $B_{\text{tok}}$, as a training plan usually does, and adding data-parallel replicas **reduces** the microbatches each replica gets, which **grows** the bubble (*Derived*). With $B_{\text{tok}} = 1{,}048{,}576$ tokens, $S = 4096$ and $b = 1$, there are 256 sequences per step. With $d = 4$ each replica gets $m = 64$ microbatches; a 4-stage pipeline idles $3/64$, about 5% of ideal time. With $d = 32$ and $m = 8$ it idles $3/8$, about 38%. More GPUs can make each GPU less efficient.

## Two worked scenarios

Both scenarios use assumed numbers, stated where they appear, so you can redo them in the planner. GB is $10^9$ bytes.

### A seven-billion-parameter model on one server

Eight GPUs in one server, an assumed usable capacity of 80 GB each, BF16 with the memory lesson's 16-byte Adam ledger.

1. **State.** Replicated data parallelism needs $16 \times 7 = 112$ GB per GPU: excluded. ZeRO stage 1 needs 38.5 GB, stage 2 needs 26.25 GB and stage 3 needs 14 GB (*Derived*, from the [memory lesson](/blog/model-development-training-memory/#work-a-seven-billion-parameter-example)).
2. **Communication.** Stages 1 and 2 move the same 24.5 GB per rank per step as plain data parallelism; stage 3 moves 36.75 GB (planner defaults, at an assumed 40 GB/s: 0.65 s against 0.97 s).
3. **Choice to pilot.** Stage 2. It leaves $80 - 26.25 = 53.75$ GB for activations, materialised parameters and buffers, and it costs no extra traffic. Stage 3 would buy another 12.25 GB of headroom for 50% more traffic.
4. **What would overturn it.** A measured peak above capacity at the planned sequence length (then try stage 3, or recomputation); or a profile showing the stage-2 parameter all-gather exposed after the optimiser step and costing more than stage 3's extra traffic would.

No model parallelism is needed: everything fits within one GPU's share once the state is sharded.

### A seventy-billion-parameter model on four servers

Thirty-two GPUs in four servers of eight, 80 GB each. Assumed: 40 GB/s per GPU between servers, 200 GB/s inside a server, 5 µs per ring step, 25 MiB buckets. A step of $B_{\text{tok}} = 1{,}048{,}576$ tokens at $S = 4096$. Model width $h = 8192$ with 80 layers, BF16.

The replicated state, $16 \times 70 = 1{,}120$ GB per GPU, is far out of reach. Compare two layouts that both fit the state (*Derived*, computed with the same tested functions as the planner):

| | A: ZeRO-3 across all 32 | B: tensor-parallel 8 inside each server, ZeRO-1 across 4 |
|---|---|---|
| Persistent state per GPU | $16 \times 70 / 32 = 35$ GB | $4n + 12n/4 = 61.25$ GB, with $n = 70/8$ billion per GPU |
| Data-parallel traffic per step | 406.9 GB per rank, all between servers: 12.66 s | 26.25 GB per rank: 0.68 s |
| Tensor-parallel traffic per step | none | 37.6 GB per microbatch, 64 microbatches: 2,405 GB inside servers, 12.0 s |
| Can that traffic overlap compute? | Mostly, in principle: gathers can be prefetched, gradient reductions overlap backward | Not by default: each all-reduce feeds the next operation |
| Activations per GPU | Each GPU holds a whole layer's activations | Split across the 8 tensor-parallel ranks |

For scale, a step is about $6 \times 70 \times 10^{9} \times 1{,}048{,}576 = 4.4 \times 10^{17}$ floating-point operations. At an assumed 40% of 312 TFLOP/s per GPU that is about 110 s of compute. On this arithmetic, layout A's 12.7 s of mostly overlappable traffic looks no worse than layout B's 12 s on the critical path. A paper calculation could talk you into layout A.

The measured evidence points the other way. *Reported, [Megatron-LM §5.2](https://arxiv.org/html/2104.04473v5):* for 175-billion and 530-billion-parameter models, PTD-P (tensor, pipeline and data parallelism combined) outperformed ZeRO-3 without model parallelism by 6% and 24% at the first GPU counts tested, and by 70% when the GPU count was doubled at the same batch size, "due to less cross-node communication". Those are different models, batch sizes and software from this scenario, so they do not settle it. They do show what the ring model leaves out: congestion when every GPU sends between servers at once, collectives that do not reach their ideal bandwidth, and overlap that is never perfect.

**Choice to pilot.** Layout B, because the closest measured evidence favours it and because it splits activations, which A does not. **What would overturn it:** a profile on your network in which A's inter-server traffic stays hidden behind compute at the planned batch, and A's activations fit. That is a cheap measurement on one or two servers before committing all four.

## A bounded experiment

The scenarios rest on two assumptions worth testing before anything else: the values of α and B, and how much of the traffic actually overlaps. A proposed pilot, **not run for this guide**:

1. **Fit the link model.** On hardware you already have, run [nccl-tests](https://github.com/NVIDIA/nccl-tests)' `all_reduce_perf` across one server, then two, from 8 bytes to 1 GB in doublings. Record framework and library versions. Fit time against size: the intercept estimates the latency term $2(p-1)\alpha$, the slope the bandwidth term. Report bus bandwidth, not algorithm bandwidth. Cap the run at ten minutes.
2. **Test the crossover.** Check that the measured crossover size is close to $p\alpha B$ from the fitted values. A large gap means the library is using a different algorithm in that size range, which is itself useful to know.
3. **Measure overlap.** Train a synthetic model of at most 100 million parameters with random tokens and no downloaded data, under DDP with `bucket_cap_mb` of 1, 25 and 256. Hold everything else fixed. Record step time and the profiler's exposed collective time. Before running, write down the prediction: very small buckets should be slower, from latency; very large ones may lose overlap.

A result that matches the predictions validates the measurement harness and the link constants, not a full-scale layout. A result that does not match tells you which assumption to replace before scaling up.

## Evidence and its limits

- **Reported:** ZeRO's stage volumes (ZeRO v3 §7); Megatron's takeaways, bubble formula and ZeRO-3 comparison, with their hardware (Megatron-LM v5); DDP's bucket default (PyTorch 2.15).
- **Derived:** the procedure's order, the coupling $B_{\text{tok}} = d\,m\,b\,S$, and every number in both scenarios, under assumptions that are illustrative and not measurements of any specific system.
- **Hypothesis:** that layout B is better for the 70-billion-parameter scenario. It is the better-supported starting point, not a result.
- **Unknown:** activation memory at the scenario's sequence length, real overlap, and network contention. These need the profile and the experiment.
