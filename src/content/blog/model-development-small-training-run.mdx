**Question: how do you know a training run is working before you spend real compute on it?**

Run checks that fail loudly on the cheap bugs before trusting the curves: the targets are the inputs shifted by one (check them directly), the first loss is close to $\ln V$ for a vocabulary of $V$ tokens (a smoke test for initialization), held-out loss on fixed batches falls, and a stop-and-resume reproduces the uninterrupted run. Then change one thing at a time and compare validation curves. In the run below, on a one-million-parameter model, skipping warmup cost 0.31 nats and a learning rate ten times too high cost 0.65, and neither failure looked like a crash.

This post puts the [training update](/blog/model-development-one-update/) from the previous post into a loop, small enough to run on a laptop CPU in about 75 seconds per run. It uses a tokenizer, a corpus split and a model architecture without explaining them; the next posts do, in order: [the corpus](/blog/model-development-pretraining-corpus/), [mixtures and repetition](/blog/model-development-data-mixtures/), [the tokenizer](/blog/model-development-tokenization/) and [the architecture](/blog/model-development-decoder-architecture/). You can come back here after them and every choice will have a reason.

## Reproduce it

Everything on this page comes from one script, `scripts/course/p6_train.py`, with pinned dependencies and a pinned input file. From a clone of the [site repository](https://github.com/richardcheam/richardcheam.github.io), with Python 3.10 to 3.12:

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r scripts/course/requirements-p6.txt     # torch 2.6.0, tokenizers 0.21.0
curl -sLo input.txt https://raw.githubusercontent.com/karpathy/char-rnn/6f9487a6fe5b420b7ca9afb0d7c078e37c1d1b4e/data/tinyshakespeare/input.txt
python scripts/course/p6_train.py input.txt --baseline-only
```

The last command trains the baseline, runs the label check and the stop-and-resume test, and writes nothing (about 3 minutes on an Apple M1). Its output should include:

```text
vocab 2048, train 346,827 tokens (2.89 chars/token), val 43,559
parameters 1,066,112; loss at initialization 7.650 vs ln V = 7.625
label check: targets equal inputs shifted by one; ...
baseline: final val 4.126, ...
resume at 300: unrounded losses, final weights and optimizer state identical: True
```

Dropping `--baseline-only` reproduces everything below: the five runs, the resume and precision checks, and the data behind Figure 1 (about 10 minutes). The script refuses any `input.txt` whose SHA-256 differs from the pinned file. Exact losses can differ in the last digits on other CPUs or PyTorch builds; the comparisons between runs should not.

## 1. Data: split first, then count passes

The corpus is Tiny Shakespeare, 1,115,394 characters of plays.

- **Split before anything else**, and contiguously: the last 10% is validation. Neighbouring lines of a play are nearly the same text, so a random split would put near-copies of validation text into training.
- **Train the tokenizer on the training split only.** A byte-level BPE with 2,048 entries gives 2.89 characters per token: 346,827 training tokens and 43,559 validation tokens.
- **Count passes.** Each step trains on 16 sequences of 128 tokens, 2,048 tokens; 600 steps are 1.23 million tokens, about **3.5 passes** over the training data. The [mixtures post](/blog/model-development-data-mixtures/#what-repeating-data-costs) explains why that number matters.

## 2. Model and the first two checks

The model is a small modern decoder: 4 layers, width 128, 4 heads, a SwiGLU feed-forward network of width 352, rotary positions, RMSNorm before each sub-layer, and tied input and output embeddings, **1,066,112 parameters** in all (the [architecture post](/blog/model-development-decoder-architecture/) explains each choice).

**Labels.** The script asserts that the targets equal the inputs shifted by one and prints a row of each. This is the check that catches a double shift or a missing one; nothing else on this page does so directly.

**First loss.** A freshly initialized model predicts close to uniformly, so its loss should be about $\ln V = \ln 2{,}048 \approx 7.62$ nats. The measured value was **7.65**. Treat this as a smoke test: a first loss of 30 means some logits start huge, and one far below $\ln V$ suggests targets leaking into inputs, but a correct first loss says nothing about whether the labels are right.

## 3. The loop

The loop is the update from the previous post, repeated:

```python
for step in range(600):
    lr = schedule(step)                       # warmup, then cosine decay
    for g in opt.param_groups:
        g["lr"] = lr
    x, y = next_batch(train_ids)              # y is x shifted by one token
    loss = F.cross_entropy(model(x).view(-1, V), y.view(-1))
    opt.zero_grad(set_to_none=True)
    loss.backward()
    norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step()
    if step % 25 == 0:
        log(step, loss, evaluate(model), norm)   # held-out loss on fixed batches
```

AdamW uses betas (0.9, 0.95) and weight decay 0.1 on weight matrices only; gradients are clipped to a global norm of 1. The learning rate rises linearly over 50 steps of **warmup**, then follows a cosine down to 10% of the peak. Warmup exists because Adam's first steps move every parameter by about the full learning rate ([previous post](/blog/model-development-one-update/#one-adamw-step)), which can push random weights somewhere they never recover from; the decay lets the loss settle at the end, so the schedule should match the run's real length (the [Chinchilla review](/paper-reviews/chinchilla/) shows how a mismatched schedule distorts comparisons).

Every 25 steps the model is evaluated on the **same** 20 validation batches. Random batches would add sampling noise to every point and hide small differences between runs.

The **baseline** (peak learning rate 0.003, 50 warmup steps) reaches a validation loss of **4.13**, a perplexity of $e^{4.13} \approx 62$. Its smoothed training loss ends near 3.88, about 0.25 below validation: partly the model fitting text it has seen three or four times, partly that the last tenth of the file is a different stretch of the plays. Watching that gap is how you would notice memorization starting.

Each other run changes one thing, and in this run:

- **No warmup** ends at **4.44**, 0.31 nats worse. It is *ahead* for the first 50 steps (6.01 against 6.18 at step 25) and behind from about step 100 on. Early speed is not a good trajectory, so judge a schedule over hundreds of steps, not dozens.
- **Peak 0.03**, ten times higher, ends at **4.77**: fast at first, then flat.
- **Peak 0.1** plateaus at **5.40**, and **5.46 without clipping**. In the baseline the gradient norm has a median of 0.57 after warmup and exceeds 1 in under 1% of steps; without clipping at peak 0.1 it exceeds 1 in 7% of steps and spikes to 15.

No run diverged to infinity or NaN. A small model with tied embeddings and pre-norm is hard to blow up, so too high a learning rate showed up here as a stall. Large models fail more dramatically, with loss spikes that may not recover, which is why large runs watch gradient norms, keep clipping on and keep checkpoints to roll back to. These comparisons are single runs of one seed on one small model: they show what each change did here, not a general ranking.

**Try it: diagnose a curve.** A colleague's run starts at 7.6, falls to 6 in 50 steps, then sits at 6 while gradient norms jump between 0.5 and 10. What would you change first?

**Answer.** The starting loss is right and early learning works, so data and model are probably fine. A plateau with spiking gradient norms is the signature of a learning rate too high for the later phase, as in the peak-0.1 runs. Lower the peak (or check the decay is actually applied), keep clipping on, and compare validation curves over a few hundred steps before committing to a long run.

## 5. Checkpoints: what the test compares

A checkpoint must hold everything that decides what happens next: weights, the optimizer's moments and step counts, the schedule position, and the data sampler's random state. Leave out the optimizer state and Adam restarts from zero moments, a sudden warmup-free jump; leave out the sampler state and the run re-reads data it has seen.

The script stops the baseline at step 300, saves the checkpoint to disk, reloads it into a fresh model and optimizer, continues to 600, and compares with the uninterrupted run. It checks three things for exact equality: the unrounded training loss at all 600 steps, every weight tensor at the end, and every AdamW state tensor at the end. All three were **identical**. Rounded losses would not be enough, since two runs can agree to four decimals while their states drift apart. Bitwise equality is the right test here because this is one CPU process with fixed seeds; on GPUs, nondeterministic kernels usually make the comparison approximate, and you would compare curves within noise instead.

## 6. Precision

Large runs compute in BF16 but keep optimizer state, and often a master copy of the weights, in FP32, because in BF16 the next number above 1.0 is 1.0078: **1.0 + 0.001 is exactly 1.0**, so a small update applied to BF16 weights can vanish. This run trains in FP32; evaluating the trained model with BF16 autocast gave a validation loss of **4.1263**, equal to FP32 to four decimals. For this model, computing activations in BF16 changed nothing measurable; the risk is in accumulating updates. The [efficient-execution post](/blog/model-development-efficient-execution/#lower-precision) covers FP16 and FP8.

A sample prompted with "ROMEO:" shows what 4.13 nats buys: the layout of a play, plausible line lengths and words, no meaning.

Ay, even thy tions to drink them, what
To over one poor behe's steeps, if you yet
Benvouned in the field, adrimling thousand
