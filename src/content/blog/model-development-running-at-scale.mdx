**Question: a large run is slower than expected and keeps getting interrupted. What do you measure, and what do you change?**

Measure **model FLOPs utilization** (MFU), the share of the GPUs' peak that goes into the model's own arithmetic, then read a profile before changing anything: large matrix multiplications should dominate, communication should overlap computation, and every rank should be equally fast. Treat failures as routine and set the checkpoint interval from the failure rate and the cost of saving; Llama 3 405B ran at 38–43% MFU and still saw an unexpected interruption every 3.1 hours. Only then revisit the layout, fitting memory first and putting the most frequent communication on the fastest links.

The previous posts each solved one problem: [data parallelism](/blog/model-development-data-parallelism/) for throughput, [sharding](/blog/model-development-sharding-recomputation/) and [model parallelism](/blog/model-development-model-parallelism/) for memory, [efficient kernels](/blog/model-development-efficient-execution/) for speed. This post is about running them together for weeks.

## Is it running well? MFU

**Model FLOPs utilization** compares the arithmetic the model needs with what the hardware could deliver:

$$
\text{MFU} = \frac{6 N \times \text{tokens per second per GPU}}{\text{peak FLOP/s per GPU}}.
$$

A 7-billion-parameter model processing 10,000 tokens per second per GPU needs $6 \times 7 \times 10^9 \times 10^4 = 420$ TFLOP/s, about **42%** of an H100's 989.5 TFLOP/s BF16 peak. MFU counts only the model's own arithmetic, so recomputation, padding and communication all lower it, which is the point: it measures useful work. (The $6N$ estimate ignores attention's FLOPs, so at long sequence lengths it understates the work slightly; Llama 3's figures include it.)

Llama 3's 405-billion-parameter model reached 38–43% BF16 MFU ([Llama 3](https://arxiv.org/abs/2407.21783), §3.3.2, Table 4):

| GPUs | Tensor | Context | Pipeline | Data | Sequence | TFLOPs/GPU | MFU |
|---|---|---|---|---|---|---|---|
| 8,192 | 8 | 1 | 16 | 64 | 8,192 | 430 | 43% |
| 16,384 | 8 | 1 | 16 | 128 | 8,192 | 400 | 41% |
| 16,384 | 8 | 16 | 16 | 8 | 131,072 | 380 | 38% |

The product of the four degrees is always the number of GPUs, and every configuration processes about 16.8 million tokens per step. Doubling the GPUs at a fixed global batch halved the batch per data-parallel group and cost two points of MFU, a typical trade.

## Where does the time go? Profiling

When MFU is low, guessing is expensive. A **profiler** records every kernel and every communication call with its duration, and shows them on a timeline. Three questions organize what you read:

1. **Which operations take the most time?** Large matrix multiplications should dominate. If elementwise operations, memory copies or data loading do, there is waste.
2. **Is communication overlapped?** On the timeline, gradient all-reduces and parameter gathers should run alongside computation. Gaps where the GPU waits for a collective mean overlap has failed.
3. **Are all ranks equally fast?** A collective finishes only when the slowest rank arrives.

A small example shows the habit. Profiling one CPU training step of a 1-million-parameter model built from PyTorch's standard `TransformerEncoderLayer` put `aten::bernoulli_`, the operation that generates dropout masks, at the top: **30%** of the step. The layer applies dropout by default, which was never intended for this model. Turning it off cut the profiled step by about a third and moved matrix multiplications and the fused attention kernel to the top. The lesson generalizes: defaults you did not choose show up in profiles, not in configuration files.

**Stragglers** are the large-scale version of question 3. Llama 3's report notes that a single slow but still-functioning GPU "can slow down thousands of other GPUs", and that even temperature mattered: throughput varied by 1–2% over the day as GPUs throttled in the midday heat (§3.3.4).

## When it breaks: failures and checkpoints

At this scale failure is routine. In a 54-day period of Llama 3 405B pre-training there were 466 job interruptions: 47 planned (maintenance, configuration changes) and **419 unexpected**, about 78% of them attributed to confirmed or suspected hardware problems, with GPU issues the largest category (§3.3.4, Table 5). That is an unexpected interruption roughly every **3.1 hours**. Despite this, the team reports more than 90% effective training time.

Recovery means restarting from the last checkpoint, which raises a trade-off. Checkpoint often and you spend time writing state; checkpoint rarely and each failure loses more work. A classic approximation (Young, 1974) puts the best interval at

$$
\tau \approx \sqrt{2 \times \text{checkpoint cost} \times \text{mean time between failures}}.
$$

With failures every 3.1 hours and an illustrative 5-minute checkpoint, $\tau \approx \sqrt{2 \times 5 \times 186} \approx 43$ minutes. Each failure then loses about half an interval, 22 minutes, plus the time to restart. The same formula says what to improve: faster, asynchronous checkpoint writes lower the cost and allow shorter intervals, which is why Llama 3's team worked on reducing checkpointing and job start-up time (§3.3.4).

A checkpoint must let the run continue exactly as if nothing happened: weights, optimizer state, schedule position and data-loader position, as the [small training run](/blog/model-development-small-training-run/#5-checkpoints-what-the-test-compares) verified on CPU by comparing unrounded losses and the final weights and optimizer state bit for bit. At scale it must also be written in shards from every rank in parallel, and be loadable onto a different number of GPUs when the cluster changes.

## Choosing a layout

The previous posts give a procedure. Work through memory first, then communication:

1. **Fit the training state.** With $N$ parameters at 16 bytes each, how many GPUs must share the state? Use tensor parallelism within a server, then pipeline parallelism or ZeRO/FSDP sharding across servers.
2. **Fit the activations.** Given the sequence length and microbatch, do activations fit? If not, use selective recomputation, an IO-aware attention kernel, or context parallelism for very long sequences.
3. **Place communication.** Put the most frequent communication (tensor parallelism) on the fastest links, inside a server; pipeline stages across servers; data parallelism over what remains.
4. **Check the batch.** The global batch is microbatch × accumulation × data-parallel ranks. Pipeline parallelism needs enough microbatches per step to keep the bubble small; data parallelism must not push the global batch beyond what the optimization can use.
5. **Measure.** Run a few hundred steps, compute MFU, read a profile, and adjust.

**Try it: lay out a 70B model.** You have 256 GPUs, 8 per server, 80 GB each, and a 70-billion-parameter model at 16 bytes per parameter. Propose a layout.

**Answer.** The state is $16 \times 70 = 1{,}120$ GB. Tensor parallelism of 8 within a server leaves 140 GB per GPU, too much. Adding 4 pipeline stages across servers divides the model over 32 GPUs: 35 GB of state per GPU, leaving room for activations, with data parallelism of $256 / 32 = 8$. Sharding the optimizer state over those 8 data-parallel ranks (ZeRO-1) brings it to about $4 \times 70/32 + 12 \times 70/(32 \times 8) \approx 12$ GB, freeing memory for larger microbatches, more of them, and a smaller pipeline bubble. An alternative, FSDP over more GPUs with less pipelining, avoids the bubble but moves more data across servers; which is faster on a given network is what step 5 decides.
