**Question: when does sharding the training state (ZeRO or FSDP) help, and what does it cost in communication?**

It helps when the model's weights, gradients and optimizer state do not fit on one GPU, because data parallelism replicates all of them on every GPU. Sharding the optimizer state, then gradients, then weights across $n$ GPUs cuts a 7-billion-parameter model's 112 GB of state per GPU to 38.5, 26.25 or 14 GB on 8 GPUs. The cost depends on the schedule: with one forward and backward pass per update, ZeRO stages 1 and 2 move as much data as data parallelism and stage 3 1.5 times as much, but with gradient accumulation stage 2 reduces gradients and stage 3 gathers weights for every microbatch. Choose the lowest stage that fits, then count transfers for the accumulation you actually use.

The other large memory consumer, activations, has a different remedy: store fewer of them and recompute the rest in the backward pass. The [GPU post](/blog/model-development-gpu-memory-compute/#what-training-keeps-in-memory) counted both; [data parallelism](/blog/model-development-data-parallelism/) is the starting point.

## Sharding the training state

**ZeRO** (the Zero Redundancy Optimizer) keeps data parallelism's structure, every GPU processing its own slice of the batch, but stops replicating the training state. Each of the $n$ data-parallel GPUs **owns** one $n$-th of it ([ZeRO](https://arxiv.org/abs/1910.02054), §5). It comes in three stages, each sharding one more part. With $N$ parameters and 16 bytes per parameter (2 for BF16 weights, 2 for BF16 gradients, 12 for FP32 master weights and moments):

| Stage | What is sharded | Per-GPU state | 7B on 8 GPUs |
|---|---|---|---|
| 0 (plain data parallelism) | nothing | $16N$ | 112 GB |
| 1 | optimizer state | $4N + 12N/n$ | **38.5 GB** |
| 2 | + gradients | $2N + 14N/n$ | **26.25 GB** |
| 3 | + parameters | $16N/n$ | **14 GB** |

The formulas are ZeRO's (§5.1–5.3). Stages 1 and 2 keep a floor that does not shrink with more GPUs: every GPU still holds full BF16 weights, and in stage 1 full gradients. Stage 3 removes the floor; with 64 GPUs it would be 1.75 GB each.

How does a GPU update parameters it does not fully hold? In stage 1, after the backward pass, each GPU applies AdamW only to its own slice of the parameters, using its own slice of the moments, and an **all-gather** then gives every GPU the full updated weights. Running this on CPU with two processes and PyTorch's `ZeroRedundancyOptimizer` (its implementation of stage 1) shows each process holding exactly half of AdamW's moments, and after three steps the parameters match an unsharded single-process AdamW to within $10^{-6}$. That implementation shards only the optimizer state, and its communication differs from ZeRO's idealized schedule: DDP still all-reduces the full gradients, and afterwards each rank broadcasts its updated shard to the others, one broadcast per rank, in FP32 on CPU (PyTorch 2.6 source).

## What sharding costs in communication

An all-reduce, the operation data parallelism uses, can be done as two halves: a **reduce-scatter**, after which each GPU holds the sum of one shard, followed by an **all-gather**, after which every GPU holds all the shards. With ring collectives, each half moves about one model's worth of gradient or weight values per GPU, $\Psi$ for $\Psi$ parameters, so data parallelism moves about $2\Psi$ per update.

ZeRO's traffic ratios rest on three assumptions: ring-style collectives, gradients and weights communicated in 16-bit precision, and **one forward and backward pass per optimizer update** (ZeRO §7). Under them:

- **Stages 1 and 2:** reduce-scatter the gradients ($\Psi$), update the local shard, all-gather the updated weights ($\Psi$): $2\Psi$, the same as data parallelism (§7.2.1).
- **Stage 3:** a GPU holds only its shard of each layer's weights, so it must all-gather them before the forward pass and again before the backward pass, then reduce-scatter gradients: $3\Psi$, **1.5 times** data parallelism (§7.2.2).

Gradient accumulation changes the count, because some transfers happen once per update and others once per microbatch. With two microbatches per update, and data parallelism skipping synchronization until the last microbatch:

| | Per microbatch | Per update | Total |
|---|---|---|---|
| Data parallel | — | all-reduce $2\Psi$ | $2\Psi$ |
| Stage 1 | — | reduce-scatter $\Psi$, all-gather $\Psi$ | $2\Psi$ |
| Stage 2 | reduce-scatter gradients $\Psi$ | all-gather weights $\Psi$ | $3\Psi$ |
| Stage 3 | gather $\Psi$ (forward), gather $\Psi$ (backward), reduce-scatter $\Psi$ | — | $6\Psi$ |

Stage 1 keeps full gradients, so it can accumulate locally and communicate once. Stage 2 keeps only its gradient shard, so each microbatch's gradients must be reduced before the rest is discarded; stage 3 must regather weights for every forward and backward pass. Implementations differ in the details, for example whether a stage-2 system keeps full gradient buffers to avoid this, so read the communication schedule of the system you use. Whether the extra traffic is affordable depends on whether it overlaps with computation.

**FSDP** (Fully Sharded Data Parallel) is PyTorch's implementation of stage 3. In the current API, `fully_shard` is applied to each Transformer block and then to the whole model. Each block's parameters are stored as shards, gathered by a hook just before the block runs and, by default (`reshard_after_forward=True`), freed after the forward pass and gathered again for the backward pass; after its gradients are computed they are reduce-scattered so each GPU keeps only its shard (PyTorch 2.6 documentation). Wrapping block by block matters: only one or two blocks' full weights exist at a time, and the next block's gather can be prefetched while the current block computes. Setting `reshard_after_forward=False` keeps gathered weights between forward and backward, trading memory for one fewer gather.


## Activations: store or recompute

Sharding addresses state, which scales with parameters. Activations scale with batch and sequence, and at long sequences they dominate: about 104 GB per sequence of 4,096 tokens for a 32-layer GPT-style model, in the [GPU post's example](/blog/model-development-gpu-memory-compute/#activations).

**Activation recomputation** (also called checkpointing) stores only each layer's input during the forward pass and recomputes everything inside the layer during the backward pass, when it is needed. Memory for a layer's internals then exists for only one layer at a time. Measuring the bytes that a small four-block network saves for backward shows the effect: 90,112 bytes when storing everything, 40,960 with each block checkpointed, and identical gradients either way.

The cost is compute. Training costs about $6N$ FLOPs per token, and recomputing every layer adds another forward pass, $2N$: about **33% more** arithmetic.

**Selective recomputation** keeps most of the saving for a fraction of the cost ([Korthikanti et al., 2022](https://arxiv.org/abs/2205.05198), §5). Recall the activation formula $sbh(34 + 5as/h)$: the $5as/h$ part comes from the attention scores, softmax and dropout, which take a lot of memory but little compute to redo. For a GPT-3-shaped model ($a = 96$, $s = 2{,}048$, $h = 12{,}288$) that part is $5as/h = 80$, more than twice the other 34. Recomputing only it, combined with sequence parallelism, reduced activation memory by 5 times and cut the time overhead of recomputation by over 90%; a 530-billion-parameter model reached 54.2% MFU instead of 42.1% with full recomputation (abstract). IO-aware attention kernels, the subject of the [efficient-execution post](/blog/model-development-efficient-execution/), avoid storing the scores in the first place.

**Try it: choose a stage.** You train a 13-billion-parameter model on 80 GB GPUs and need about 25 GB per GPU for activations and buffers. Which ZeRO stage fits on 8 GPUs? On 16?

**Answer.** On 8 GPUs, stage 2 needs $2 \times 13 + 14 \times 13/8 \approx 48.8$ GB of state, plus 25 GB: about 74 GB, which fits with little margin. Stage 3 needs $16 \times 13/8 = 26$ GB, plus 25: 51 GB, comfortable. On 16 GPUs, stage 2 needs about 37.4 GB of state and fits easily, avoiding stage 3's extra communication, 50% more without accumulation and more with it. The answer depends on the GPU count: more GPUs make the cheaper stage fit.
